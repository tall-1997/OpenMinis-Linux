# Foreground notification publishing

`AgentForegroundService` owns notification `agent_status/9001`. It performs one plain, cheap `startForeground` in `onCreate` to meet the Android FGS deadline. All subsequent updates (tracker events, Live Updates toggle and recents-task re-anchor) enter `requestStatusRefresh`; **only `applyForeground` calls `startForeground`**. START_STICKY with an empty in-memory tracker stops instead of restoring an orphan task.

`SessionActivityTracker.notificationTimeline` publishes a coherent run boundary after the active set, start clock and finish clock have settled. This avoids posting a new run with the old clock or a finished task still ticking. `ForegroundNotificationState` is a snapshot of visible content, not the raw stream: per-token status, freeform tool title and wall-clock ticks never enter its identity. `ForegroundNotificationPolicy` records only *successful* publishes; every delayed callback reads a new snapshot and rechecks the ledger. Recents-task removal may re-anchor once independently of content deduplication.

For promoted ongoing notifications, `stableForPromotion` removes individual tool/progress changes. The chip is requested only while active jobs exist **and** the user has enabled Live Updates and the system grants the capability. Its critical text is constant; elapsed time uses the system chronometer. Start, end, change in concurrent job count, new run clock and promotion-mode changes are immediate. Ordinary foreground rows may reflect tool changes, coalesced to 5 seconds; there is no periodic refresh. A finished task falls back to a normal ongoing foreground row while chat presence still requires the service.

The service keeps the ordinary notification when Live Updates is off. The app-side change prevents repetitive chip re-inflation; it does not assert that a single promoted notification cannot trigger a ROM-side leak. On HyperOS, compare identical workloads with Live Updates on/off, inspect `dumpsys notification` for repeated id=9001 enqueues, and trend post-GC SystemUI heap troughs for several hours. Do not interpret one heap sample as proof of a leak or a cure.

Verification: `:app:compileDebugKotlin :app:testDebugUnitTest --tests com.openminis.app.service.ForegroundNotificationPolicyTest`. Android packaging additionally requires an **arm64 SDK CMake 3.22.1** and NDK configured by the project; Kotlin-only checks do not prove native packaging or OEM runtime behavior.
